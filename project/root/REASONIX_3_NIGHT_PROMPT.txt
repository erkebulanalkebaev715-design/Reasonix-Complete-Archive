REASONIX 3.0 — REAL SWARM
==================================================

Reasonix 3.0 must implement a genuine core swarm runtime.

It is NOT:
- multiple chat completions concatenated;
- a frontend simulation;
- several fake worker cards.

Required architecture:

1. SWARM ORCHESTRATOR

Own the global objective.

Decide dynamically:
- whether swarm is useful;
- task decomposition;
- dependencies;
- worker count;
- worker profiles;
- providers/models;
- concurrency;
- budgets;
- stop conditions;
- verification;
- result integration.

A trivial task must not launch unnecessary workers.

2. STRUCTURED TASK GRAPH

Maintain explicit task state such as:
- id;
- objective;
- status;
- dependencies;
- worker;
- model/provider;
- scope;
- evidence requirements;
- result;
- failure;
- retry count;
- timestamps.

Raw transcripts are not authoritative swarm state.

3. CONFIGURABLE AGENT PROFILES

Examples may include:
Architect
Researcher
Coder
Debugger
Tester
Verifier
Integrator

But generic architecture must not depend on these exact names.

Worker profiles may control:
- instructions;
- Tools;
- Skills;
- provider/model preference;
- context;
- budget;
- timeout;
- evidence requirements.

4. DYNAMIC WORKERS

Give each worker:
- bounded objective;
- relevant context only;
- dependencies;
- allowed tools;
- budget;
- workspace/artifact scope;
- output contract.

Do not feed full project history to every worker.

5. PROVIDER-AGNOSTIC EXECUTION

Generic swarm architecture must not hardcode DeepSeek or Kimi.

It must operate against configured Reasonix providers.

Initial important real integrations:
- DeepSeek;
- Kimi/Moonshot when credentials/config exist.

6. STRUCTURED SHARED STATE

Exchange:
- findings;
- decisions;
- artifacts;
- patches;
- evidence;
- errors;
- test results;
- references.

Do not copy every complete worker transcript to every worker.

7. BOUNDED PARALLELISM

Actually execute independent tasks concurrently.

But enforce limits appropriate for Android ARM64:
- worker count;
- CPU/RAM pressure;
- concurrent provider requests;
- provider limits;
- monetary budget.

8. MUTATION OWNERSHIP

Workers must not blindly edit the same file concurrently.

Implement an architecture appropriate to existing Reasonix, possibly:
- ownership;
- isolated workspaces;
- patch artifacts;
- staged merge;
- conflict detection;
- integration coordinator.

Choose based on actual code.

9. RESULT INTEGRATION

- runtime event;

- read-back;
