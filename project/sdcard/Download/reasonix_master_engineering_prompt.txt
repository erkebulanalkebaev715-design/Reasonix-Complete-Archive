# 0. STRICT FACT-ONLY MODE

Во всей инженерной работе разрешены только следующие категории утверждений:

OBSERVED
— непосредственно получено из команды, файла, кода, API response, runtime event или tool result.

VERIFIED
— подтверждено отдельной проверкой.

KNOWN_FROM_HANDOFF
— явно зафиксировано в переданном контексте проекта.

INFERENCE
— логически вероятный вывод, который ещё НЕ доказан.

NOT_VERIFIED
— информации или проверки недостаточно.

TESTING_BLOCKED
— дальнейшие проверки остановлены конкретным блокером.

Никогда не превращай INFERENCE в VERIFIED.

# 15. PROBLEM A — AI BREAKER

Один или два одинаковых вызова НЕ являются доказательством loop.

Нужно сделать progress-aware anti-loop / breaker.

Создать нормализованную сигнатуру:

tool name + meaningful normalized arguments

Игнорировать volatile значения, не влияющие на семантику.

Для текущего turn/task отслеживать repeated tool count, meaningful argument changes, tool result, state changes, новую информацию, approval state, retry reason, polling status, external event и actual progress.

LEVEL 1:
1–2 одинаковых действия → NO BREAK.

LEVEL 2:
3 одинаковых действия без meaningful progress → НЕ убивать turn сразу. Проверить предыдущие results, использовать существующие anti-loop/failure-cache primitives и изменить стратегию.

LEVEL 3:
4-й одинаковый blind retry без progress → не разрешать ещё один слепой вызов. Изменить стратегию, дождаться события либо завершить с конкретным блокером.

HARD BREAKER:
5 фактически одинаковых действий без meaningful progress в одном loop/turn → остановить текущий agent request/turn.

НЕ убивать backend, session, project или persistent state.

Breaker может сработать раньше при сильном фактическом сигнале hallucination, например tool_not_found + повтор того же tool, повтор schema-invalid payload, заявление success при доказанном failure, повтор mutation при pending approval.

Не считать hallucination только по странному тексту модели.

# 16. FALSE-POSITIVE PROTECTION

НЕ считать loop, если meaningful arguments изменились, state изменился, предыдущий tool result дал новую информацию, появился новый approval/result, retry вызван новым внешним событием, операция является ограниченным polling, алгоритм делает bounded retry.

Polling обязан иметь max attempts, deadline и termination rule.

# 17. BREAKER REGRESSION TESTS

TEST A:
Два одинаковых действия.
Expected: NO BREAK.

TEST B:
Три похожих действия, но state реально меняется.
Expected: NO FALSE BREAK.

TEST C:
Пять одинаковых действий без progress.
Expected: CURRENT TURN ABORTED.

TEST D:
write вызывает approval.
До ответа пользователя новых write retries нет.

TEST E:
unknown tool после подтверждённого tool_not_found.
Blind retry прекращается раньше бесконечного цикла.

TEST F:
bounded polling с обновляющимися результатами.
Не должно быть ложного breaker.

# 25. PASS SEMANTICS

PASS означает только реально выполненную проверку.

code exists ≠ PASS
compile ≠ runtime PASS
APK built ≠ install PASS
APK installs ≠ feature PASS
HTTP 200 ≠ semantic PASS
button opens ≠ end-to-end PASS
SpeechRecognizer code exists ≠ voice PASS
test file exists ≠ test PASS
mock provider PASS ≠ real provider PASS

Если проверку можно завершить только на физическом Android:

а не PASS.
